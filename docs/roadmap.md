# 開発ロードマップ

このドキュメントは、プロジェクト制作全体の進行指針です。  
現在すでに実装済みの機能があるかどうかはここでは考慮しません。  
必要なことを漏れなく整理し、今後はこの順序で実行します。

## 位置づけ

- このロードマップは「暫定版の全体方針」として扱う
- 技術選定・仕様・優先順位が確定するたびに見直す
- 仕様や技術の変化があった場合は、次回の見直し対象として更新する

## 見直しサイクル

- 主要な仕様変更があったとき
- 重要な技術選定が確定したとき
- フェーズの進行に合わせて見直す

## 基本方針

- 迷ったときはこのロードマップに戻る
- 各フェーズで完了条件を定義し、達成してから次へ進む
- 同じ内容を別ドキュメントへ重複記載しない
- 仕様は一次情報へリンク参照する

## 最小公開方針（個人開発）

- まずはMVP公開を優先し、必須でない高度な運用は公開後に段階導入する
- 品質ゲートは「lint / typecheck / test」を最小セットとして必須化する
- 監視はVercel標準ログとエラー監視の最小構成から開始する
- セキュリティは「認証・RLS・シークレット分離・依存関係監査」を公開前の必須項目とする
- ドキュメントは運用に必要な手順のみ残し、重複や過剰な詳細は避ける

## Phase 1: 目的・仕様の固定

目標:

- プロダクトの目的、対象、非機能条件を言語化する
- 主要仕様の境界を明確化する

タスク:

- [ ] 目的・対象ユーザー・提供価値の整理
- [ ] 主要機能のスコープ定義
- [ ] 技術構成と選定方針の確定
- [ ] サーバー/バックエンドの責務範囲整理
- [ ] 認証方式と利用範囲の整理
- [ ] データ保存先と初期データモデルの整理
- [ ] 環境変数・シークレット管理方針の整理
- [ ] 地域選択仕様の確定
- [ ] 服装推薦仕様の確定
- [ ] 用語集（気温帯、朝夕、日中など）の統一
- [ ] ドキュメントの参照構造整備
- [ ] リリース可否判断に使う最小チェックリスト（Go/No-Go）を定義

完了条件:

- 各仕様に未決定項目が残っていない
- 技術選定の理由と未確定事項が文書化されている
- サーバー/バックエンドの責務範囲が明確になっている
- 実装チームが「次に何を作るか」を仕様から一意に判断できる

## Phase 2: コア体験の実装

目標:

- 起動直後に天気と服装がわかる最短導線を成立させる

タスク:

- [ ] 地域選択フロー（地方→都道府県→市区町村）の実装
- [ ] 予報データ取得と表示（ローディング・エラー含む）
- [ ] 日中/朝夕の服装表示の実装
- [ ] モバイル優先レイアウトの最適化
- [ ] localStorage連携による選択地域の保存/復元
- [ ] 主要画面の遷移と状態管理の整備

完了条件:

- 初回利用でも主要画面に迷わず到達できる
- 地域変更から表示更新までの一連動作が安定している

## Phase 3: 服装推薦の精度向上

目標:

- 気温帯にもとづく推薦ロジックを実運用レベルに引き上げる

タスク:

- [ ] 気温帯ルールの明文化と実装
- [ ] 日中と朝夕の差分ロジック整理
- [ ] 極端な高温/低温・欠損値などのエッジケース対応
- [ ] 予報更新時の再計算タイミング最適化
- [ ] 推薦結果の説明性向上（なぜその服装か）
- [ ] 代表的な気温ケースの回帰テスト整理

完了条件:

- 代表的な気温ケースで期待する推薦が再現できる
- 仕様変更時にルールを追従しやすい構造になっている

## Phase 4: ユーザー別カスタマイズ

目標:

- 家庭ごとの好みに合わせて継続利用しやすくする

タスク:

- [ ] 服装アイテムの追加・編集・削除
- [ ] 気温帯ごとの服装セット編集
- [ ] ユーザー設定の保存・復元
- [ ] 認証導線とデータ保存設計
- [ ] サーバー/APIの責務整理と必要エンドポイントの明確化
- [ ] Supabaseテーブル設計とRLS方針の確定
- [ ] 環境変数・シークレット・デプロイ設定の整理
- [ ] 設定変更の失敗時リカバリー（バリデーション・ロールバック）

完了条件:

- ユーザーが自分の運用に合わせた設定を継続できる
- 設定データ破損や不整合時の復旧手段がある

## Phase 5: 品質保証と運用基盤

目標:

- 安全に変更できる開発運用を整える

タスク:

- [ ] 単体テスト整備（ロジック中心）
- [ ] コンポーネントテスト整備（主要UI中心）
- [ ] E2Eは主要1導線（初回利用→地域選択→予報表示更新）のみ実装
- [ ] CIでのlint/test/typecheck実行
- [ ] Vercelデプロイ方針と環境変数運用の確定
- [ ] サーバー/バックエンド周辺の監視・ログ運用方針の策定
- [ ] 本番環境における認証・DB・シークレットの運用手順整理
- [ ] エラー監視・ログ運用方針の策定
- [ ] 依存関係の脆弱性監査（`pnpm audit` など）の実行ルールを定義
- [ ] 障害時の一次対応Runbook（確認手順・切り戻し判断）を作成

完了条件:

- 主要機能に回帰検知ラインがある
- PR時の最低品質ゲートが機能している
- `main`向けPRで必須チェック（lint/test/typecheck）が常時通過する
- 主要1導線のE2Eが安定して通る

## Phase 6: リリース準備と継続改善

目標:

- 継続公開に耐える形でリリースし、改善サイクルを回す

タスク:

- [ ] パフォーマンス最適化（初期表示、画像、再描画）
- [ ] アクセシビリティ改善
- [ ] リリースノートと運用手順整備
- [ ] リリースチェックリスト（Go/No-Go）に基づく最終確認
- [ ] ロールバック手順（アプリ設定・DB変更の戻し方）の明文化
- [ ] ユーザーフィードバック収集導線
- [ ] 次期ロードマップ更新

完了条件:

- リリース手順が明文化され再現可能
- 改善要望を次スプリントへ接続できる
- 公開後1週間の監視・復旧フローが運用できる

## 横断バックログ

以下は特定フェーズだけでなく継続的に扱う。

- 文言統一（子どもにも伝わる語彙）
- デザイン整合性（コンポーネント利用統一）
- セキュリティと個人情報の最小化
- ドキュメント更新の同期

## 運用ルール

- 新しいIssueは、必ずこのロードマップ上のフェーズに紐づける
- フェーズ外の作業は「例外タスク」として理由を記録する
- フェーズ完了時に、次フェーズ開始前の見直しを行う
